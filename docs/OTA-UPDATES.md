# OTA1.1.9

27 октября2026. Реализация: signed catalog `ota-manifest.cjs`, GitHub streaming `github-updater.cjs`, композиция `ota-stage.cjs`, штатные дельты `file-update.cjs`, запасные application-components `runtime-update.cjs` и Windows helper. Профиль и музыка не являются частью дерева установки и в пакеты не попадают.

## Поддерживаемые основы и старые загрузчики

Стабильные1.1.0–1.1.8.3:19 выпущенных основ, восстановленных из опубликованного1.1.0 EXE и подписанных последующих пакетов, с проверкой опубликованных SHA256, подписей и всех конечных файлов. Каталоги не строятся по рабочей пользовательской установке. Provenance и стенд — work/ota119 вне репозитория; hardlink-копии неизменяемого runtime не меняются на месте.

Старый загрузчик ищет только `Wave-V.waveupdate` и проверяет одну exact baseVersion. Это нельзя исправить добавлением JSON в GitHub. Канонический пакет1.1.9 сохраняет переход от1.1.8.3. Для остальных19 основ публикуются именованные `from-V` пакеты, совместимые со старым WAVEUPD2 и действующим ключом. Один ручной выбор маленького файла переводит сразу на1.1.9; обязательного100МБ EXE или установки всех промежуточных выпусков нет. Автоматический подбор манифеста начинается с1.1.9. Альфы/беты и изменённые основы не включены в окно поддержки; опубликованные артефакты прошлых версий не заменяются.

## Подписанный каталог и подбор

`Wave-V-ota.json` содержит подписанную строку payload: schema/product/arch/channel/version и максимум256 рёбер. Каждое ребро задаёт from/to, размер, SHA512, kind и HTTPS-URL в релизах arthurhoodwin/wave. Используется прежний закреплённый Ed25519-ключ. JSON из GitHub без подписи не определяет путь установки. Тег релиза и целевая подписанная версия должны совпадать; при испорченном каталоге нет молчаливого перехода на непроверенный источник.

Минимизация суммы байтов по возрастающему графу версий, максимум24 пакета, без циклов/даунгрейда. Есть прямые рёбра из поддержанных основ и опубликованные промежуточные рёбра; при меньшем размере выбирается цепочка. Размер в UI — суммарная загрузка, а не каждый пакет по отдельности. Малые пакеты показываются в КиБ. Доступен ручной выбор файла.

## Подготовка и откат

Каждый файл потоково скачивается в уникальный temp, ограничивается опубликованным размером, проверяется SHA512 из signed catalog, затем отдельно подписью собственного envelope. Разрешены только GitHub release URLs и его asset CDN, до5 перенаправлений, credentials omit. Нет передачи VK-токена или коллекции. Cancel/ошибка удаляет временные загрузки, не выдаёт staged success.

Композиция происходит вне программы: проверяется исходная база, реконструируются изменённые файлы каждой ступени, проверяется промежуточное target дерево. Неизменный runtime не копируется целиком в staging и не скачивается заново. Только финальные отличия записываются в один plan; rollback содержит реальные исходные файлы. До commit установки профиль/программа не меняются. Диск проверяется перед загрузкой и перед записью forward/rollback; недостаток места или ошибка оставляют приложение прежним. Границы:2ГиБ целевой сборки, ограниченные декодеры/списки; крупные компоненты требуют достаточной RAM.

Запасной `WAVEUPD3` содержит application-components и подписанные hashes общего runtime. Для Wave.exe общие content-defined блоки могут браться из локального исполняемого файла по SHA512, а отличающиеся входят в пакет; финальный полный hash обязателен. Файлы Electron/resources, не меняющиеся между версиями, не передаются. Это не универсальный патч для произвольного изменённого runtime: несовпадение прекращает подготовку. Смена Electron требует новых файлов или установщика, постоянный размер не обещается.

Windows helper повторно проверяет исходные hashes, staged hashes и пути без junction/symlink. Намерение операции сохраняется в journal до rename; при обычной ошибке откат немедленный, при прерывании следующий вызов recovery восстанавливает transaction. Мarker committed отличает успешную транзакцию от незавершённой. После восстановления запуск повторяется. Если прервано обновление настолько, что приложение вообще не может загрузить свой main-код, нужен повтор helper/полный установщик: обещать автоматическое восстановление неработающего загрузчика нельзя. Сам журнал не является страховкой от физической поломки диска.

## Выпуск

`scripts/package-update.cjs`: exact-base WAVEUPD2 или runtime-компоненты; `scripts/package-ota.cjs`: сначала проверяет envelope каждого файла, затем подписывает граф. `package.json.otaBases` определяет обязательные direct-файлы. `scripts/release.cjs` требует весь набор и суммы до публикации; ранее опубликованные assets не перезаписываются. Сначала небольшие файлы, EXE отдельно, повтор пропускает уже проверенные digest.

Результаты интеграций, размеры и ограничения публикуются в [VALIDATION.md](VALIDATION.md), описания релизов остаются пользовательскими.

Воспроизведение стенда: `node scripts/acquire-ota-bases.cjs <новая-папка-стенда>` (gh с доступом GitHub и существующий упаковщик electron-builder), затем `node scripts/build-ota-release.cjs <стенд>/bases <ключ-подписи> <стенд>/provenance.json`. Исторические деревья нужны только при сборке/приёмке; после проверки они удаляются, остаются provenance/пакеты и текущая каноническая win-unpacked. Неизменяемые файлы стенда могут быть hardlink: код всегда заменяет файл целиком, не пишет в связанный файл на месте.

Уточнение совместимости: новый журнал восстановления относится к установкам новым helper. Первый переход из старого клиента выполняет его исторический helper; этот путь отдельно проверен на установку/откат, но новый механизм recovery не может задним числом изменить старый выполняемый процесс.
