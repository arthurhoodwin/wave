### Реальный дефект: теряется часть выделения при скачивании

**Источник:** [personal.js:33](../src/renderer/personal.js#L33), `download(ids)` передаёт `ids.slice(0,100)`, затем без уточнения количества показывает «Добавлено в загрузки».

**Воспроизведение:** текущая функция выполнена в VM с 150 искусственными идентификаторами и подменённой `command`. Выбрано 150, отправлено 100, последний — track-99, сообщение — «Добавлено в загрузки». Запросы к VK/аудиосерверу не выполнялись. Результат стенда: `work/roadmap-download-selection-audit.json` вне репозитория.

**Дополнительная граница:** download-manager.cjs:17,20 допускает до 100 записей за запрос и до 100 активных задач. Поэтому простая разбивка на несколько одновременных запросов по 100 не решит задачу — следующая порция столкнётся с заполненной очередью.

**Что нужно сделать:** убрать молчаливую потерю выбранных песен. Для большого списка организовать сохранённый план/порционную подачу с учётом ёмкости очереди, корректными итогами и продолжением после перезапуска. Как минимум, до выполнения сообщать явное ограничение вместо тихого обрезания; одной такой надписью нельзя объявлять полное скачивание больших плейлистов реализованным.

Выбор «Все в этом списке» в collection-tools.js использует `state.viewTracks || state.tracks`: это доступное представление списка. Пока удалённый список загружен частично, нельзя называть его всей серверной коллекцией. При доработке нужно явно учитывать фильтр, полноту списка и выбранные идентификаторы; не возвращать отдельные лишние кнопки «Скачать список/песню», ранее убранные владельцем.

### Точные ограничения, не обязательные новые функции 1.1

- Прямой файл продолжается только при подтверждённой неизменности strong ETag; без неё начинается заново. HLS после паузы начинается заново.
- В одной текущей очереди — до 100 активных задач, в локальном каталоге — до 5000 записей; один файл — до 512 МиБ, операция загрузки ограничена 10 минутами.
- Новые скачивания сохраняют JSON-метаданные и отдельную обложку. Встроенные ID3/MP4-теги и дополнение обложек старых копий **не реализованы**, но не являются условием уже согласованного офлайн-воспроизведения.
- Подборки зависят от доступного каталога конкретного аккаунта VK; собственного рекомендательного сервиса нет и не обещалось.
- Автоматическая проверка GitHub ориентирована на стабильный Latest, а импорт Beta выполняется вручную. Это текущий выбор канала, не дефект обнаружения предварительных выпусков.
- При отключении питания посреди замены файлов полного атомарного отката нет; доступен полный установщик. Файловый откат и обработка обычной ошибки записи реализованы.

### Что изменилось в плане

1. Снять общие задачи «дописать HLS/офлайн/обрывы/откат» как вводящие в заблуждение — механизмы существуют.
2. **Beta 8:** устранить найденное обрезание большого выделения; обеспечить понятный и полный результат скачивания большого списка в пределах лимита каталога. Подготовить подписанный небольшой пакет от точной Beta 7, прогнать настоящий Electron-цикл обновления/отката.
3. В рабочей установке владелец подтверждает переход Beta 7 → следующий выпуск; VK-лайки и реальную выдачу подборок также проверяет вручную. Эти пункты не объявлять выполненными без результата.
4. После этого — **RC 1** с зафиксированным составом функций. Исправлять конкретные найденные дефекты, а не добавлять новые общие направления.
5. Независимая Windows-машина/VM остаётся внешним пробелом проверки; владелец сообщил, что такой среды нет. Не представлять её как выполненную и не обещать провести автоматически. В релизном решении явно учитывать эту границу.
6. Многочасовые прогоны и профилирование памяти не возвращать в обязательный план без отдельного согласования; ранее владелец оставил из соответствующего блока только офлайн.
7. Встроенные теги и переобработка старых обложек — перспективные улучшения без назначенного выпуска, не причина задерживать текущую 1.1.

## Конкретные пробелы, влияющие на порядок работ

1. **Отмена в backend не означает доступность переключения в UI.** `src/main/native-player.cjs` отменяет старые команды поколениями, но `src/renderer/app.js` оставляет клик по строкам доступным, однако next/previous блокируются через `state.busy`, а транспортные пути имеют собственные guards. Критерий мгновенной отмены нужно проверять по всем путям выбора, а не объявлять выполненным по одному тесту NativePlayer.
2. **Текст из кэша не всегда показывается офлайн.** `src/main/vk-http.cjs:lyrics` имеет ограниченный кэш, но `provider.cjs:lyrics` сначала требует online; сетевой метод начинает с connect. Повторное открытие без сети пока нельзя обещать.
3. **Лайк хранится в нескольких местах.** Backend обновляет записи по native key, renderer после операции — по UI trackId. Тот же трек из поиска и медиатеки может иметь разные UI ID. Нужна единая модель состояния, без сведения разных версий песен по одному названию.
4. **История навигации ≠ история прослушивания.** `navigation.snapshots` сохраняет открытые виды; `state.history` — временное состояние плеера. Это не готовый источник постоянного раздела «Недавно прослушанное».
5. **Внутренние счётчики ≠ диагностика для пользователя.** `VkHttpClient.stats` есть, но безопасного экспортируемого отчёта нет.
