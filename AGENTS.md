# Работа над Wave

## Быстрый старт

Рабочий корень — этот репозиторий. Начните с git status и целевых src/tests. Текущие требования — docs/ROADMAP.md; карта документов — docs/STRUCTURE.md. История — docs/archive/, читать только по конкретной необходимости. Не загружайте целиком исторические отчёты в контекст каждой задачи.

Граф используйте для поиска связей коротким запросом, затем сверяйте целевые исходники. Не перестраивайте весь граф ради небольшого исправления; устаревшие связи не заменяют чтение кода.

## Итерации и проверки

- Сначала закончите изменение, затем проверяйте затронутую подсистему. Не меняйте соседние функции на основании гипотетических проблем без подтверждения или необходимости для задачи.
- Документация: ссылки, diff и визуальная проверка при необходимости. Не собирать EXE и не запускать Electron ради изменения текста.
- Код: во время итерации запускайте нужные tests/*.test.cjs адресно. Перед завершением изменения один полный npm test: он занимает около5секунд. Не удаляйте полезное покрытие ради этой небольшой экономии.
- Electron: test:artists-electron для артистов, test:discovery-electron для главной/альбомов, test:updates-electron для упаковки/обновлений. Для выпуска один итоговый прогон всех гейтов после последних соответствующих изменений.
- Повторный прогон нужен при изменении проверяемого кода, падении или новой подтверждённой проблеме. Не повторять зелёные проверки после правок только документации.
- Изолированный стенд важнее управления рабочим окном. При сбое native input — одно обновление состояния/восстановление и одна подходящая альтернатива; затем прекратить одинаковые попытки. Для доступа к рабочему сеансу учитывать действующее разрешение пользователя, не копировать/не расшифровывать профиль вручную.

## Сборка и выпуск

Собирайте финальную поставку один раз после стабилизации кода и package.json. Сохраните точную предыдущую win-unpacked до пересборки. Изменение src, package.json, упакованных build-файлов требует новой сборки; изменение внешних docs/tests само по себе — нет. Не используйте промежуточную сборку с тем же номером как каноническую основу патча. Сразу после копирования основы сверить каждый файл с target подписанного опубликованного пакета её версии; FileVersion и число файлов недостаточны. Не подписывать delta от повреждённой временной копии.

Один успешный CI на точном релизном коммите достаточен. Не ждать второй идентичный job ветки и тега. Публикация — resumable draft: небольшой пакет и суммы сначала, полный EXE отдельно, с проверкой digest. При проблеме сети возобновлять отсутствующий файл, не пересобирать и не отправлять уже проверенные файлы заново. После сбоя Git TLS допустим ограниченный повтор с `git -c http.version=HTTP/1.1`; не отключать проверку TLS.

Проверенные локальные артефакты можно установить по действующему поручению пользователя об автоматическом обновлении, не откладывая это только из-за медленной загрузки EXE на GitHub. Никогда не называть релиз опубликованным, пока полный комплект не проверен.

После выпуска сохранить текущую каноническую win-unpacked, убрать только известные старые артефакты/свои временные копии. Не обновлять версию приложения ради изменения рабочего процесса или документации.

## Общение

Кратко сообщайте результат и реальную неопределённость. Не разворачивайте повторно длинное исследование уже установленных фактов. Описание релиза — для пользователя, без числа тестов и внутреннего протокола.
